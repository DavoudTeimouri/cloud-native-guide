# 6.14 Alert Management

## Purpose and scope
Alert rules, severity classification, notification channels, alert routing, alert grouping, escalation, silence management, alert testing, operational response procedures.

## Alert rules
Categories: cluster (API server, scheduler, controller-manager, etcd), node (kubelet, node_exporter, CPU, memory, disk), storage (Ceph, Rook-Ceph, ceph-csi, PVC), platform (Rancher, Argo CD, Keycloak, GitLab, Harbor, Vault), GPU, ingress.

## Severity
| Severity | Meaning | Response time | Example |
|---|---|---|---|
| Critical | Service outage or data loss risk | Immediate (15 min) | etcd down, API server unreachable |
| Warning | Degraded performance or capacity risk | Within 1 hour | Node CPU > 85%, disk > 80% |
| Info | Informational, no immediate action | Next business day | New version available, deprecated API |

## Routing
Alertmanager routes based on severity, cluster, service:
- Critical → internal SMTP smarthost / Matrix #critical-alerts (PagerDuty/Slack optional fallback in connected env)
- Warning → internal SMTP / Matrix #warnings-alerts
- Info → internal SMTP / Matrix #info-alerts

Air-gapped: route to internal notification only; SaaS receivers unreachable.

## Silencing and escalation
- Silences time-bound with reason and owner.
- P0 auto-escalates to on-call lead after 1 hour.
- P1 escalates after 2 hours if no progress.
- Every alert links to a runbook.

## Alert lifecycle
1. Fire: rule condition met for `for` duration.
2. Notify: Alertmanager sends to routed receiver.
3. Acknowledge: on-call acknowledges; incident declared.
4. Resolve: condition clears; auto-resolve; post-incident review within 5 working days.

## Validation
- Every alert has runbook link and named owner.
- Cluster-level inhibition prevents one node failure from hundreds of pages.
- Silence is itself an alert: Prometheus that cannot scrape target produces "no data" alert.
- Paging only on symptoms users feel (availability, latency, data loss risk); everything else a ticket.
