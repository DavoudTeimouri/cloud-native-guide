# GitOps and Application Delivery

## Purpose and scope
Argo CD installation on management cluster, Git repository integration, AD/LDAP authentication, local authentication, RBAC, AppProjects, Applications and ApplicationSets, repository credentials, image synchronization, offline GitOps, multi-cluster deployment, sync policies and drift detection.

## Principle
GitLab CI builds container images and Helm charts; Argo CD declares the desired Kubernetes state. Developers push to GitLab; Argo CD converges the cluster to match. No kubectl apply or helm install by hand on production clusters.

## Install
Argo CD v3.5.6 (chart 10.10.5) + ApplicationSet chart 1.12.1, installed on the management cluster via Helm from the internal Helm repository.

## Authentication and authorization
- Humans authenticate through Keycloak (OIDC). No shared accounts except documented break-glass.
- Local Argo CD admin password stored in Vault; break-glass only.
- RBAC: namespace-scoped for application teams; cluster-admin held by two named operators.
- Service accounts are per-application, never shared.

## Repository integration
- Argo CD syncs from GitLab repositories containing Helm charts and kustomize/manifests.
- ApplicationSet controllers generate Applications from GitLab project metadata.
- Image Updater tracks new image tags in Harbor and updates Application values (GitOps promotion workflow).

## Sync policies
- Applications use Automated sync with Prune and SelfHeal enabled for production.
- Promotion workflow: dev -> staging -> prod, each a separate Application/ApplicationSet.
- Drift detection: Argo CD reports OutOfSync when live state diverges from Git; alerts fire.

## Multi-cluster
- One Argo CD instance (management cluster) manages multiple application clusters via cluster registration.
- Each application cluster is an Argo CD cluster secret; Applications target specific clusters by name.

## Offline GitOps
- All charts and images mirrored to internal Harbor/Helm repo; no public access at runtime.
