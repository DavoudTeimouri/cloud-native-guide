# Architecture

## Purpose and scope
Document highly available load balancing architectures for the Cloud-Native stack: Active/Active preferred where supported, HAProxy/NGINX/other enterprise solutions, Keepalived VIP management, management-cluster and application-cluster load balancers, deployment methods (native and Docker Compose), HA, health checks, TLS, and failover testing.

## Architecture principles
- **Active/Active preferred**: two VIPs balanced by router ECMP/BGP. A single VRRP VIP is Active/Standby, not Active/Active.
- **Tiered edge**: Tier 1 external edge (HAProxy L4 + Nginx L7 on host network via Docker Compose, Keepalived unicast peers); Tier 2 in-cluster MetalLB; Tier 3 DNS/GSLB.
- **Management vs application separation**: dedicated LB pairs for management clusters; optional dedicated pairs per application cluster.
- **Default deny**: only explicitly allowed ports are open; every open port justified and documented in the network matrix.

## Components
- HAProxy: L4 load balancing with active health checks, used for control-plane VIP and management services.
- Nginx: L7 load balancing and TLS termination, used for ingress and external-facing services.
- Keepalived: VIP management and failover with unicast peers.
- MetalLB: in-cluster LoadBalancer IP assignment for application clusters (v0.16.1).
- F5 NGINX Ingress Controller chart 2.8.0 + NGINX Gateway Fabric + Gateway API CRDs v1.6.3: L7 ingress.

## Control / data plane split
External edge VIPs are separate from the Kubernetes data-plane network. The control-plane VIP is separate from the data-plane network, so network misconfiguration is isolated to the affected pod or service; cluster-wide API access remains unaffected.
