# Infrastructure Sizing and Resource Calculation

## Purpose and scope

Practical sizing methodology with real calculations based on measured metrics: CPU, memory, storage capacity and IOPS, network bandwidth, control-plane nodes, workers, Ceph roles, load balancers, repositories, GitLab, monitoring/logging, and operational servers. Each formula includes a worked example so you can reproduce it for your environment. Minimum, recommended, and production configurations are given at the end.

## Calculation formulas

### CPU cores

```bash
Required vCPU = (Expected pods × Cores per pod) / CPU utilization target
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Expected pods | Workload-dependent | Peak concurrent pods across the cluster |
| Cores per pod | 0.25–1.0 | Application-specific; measure with `kubectl top pod` |
| CPU utilization target | 0.70 | Keep headroom for bursts and rolling upgrades |

**Example**: 500 pods × 0.5 cores per pod ÷ 0.70 = 358 vCPU → round up to 360 vCPU across the cluster. With 8-core nodes, that is 45 worker nodes.

### Memory

```bash
Required RAM = (Expected pods × Memory per pod) / Memory utilization target + OS overhead
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Expected pods | Workload-dependent | Peak concurrent pods |
| Memory per pod | 256–1024 MiB | Measure with `kubectl top pod`; include sidecars |
| Memory utilization target | 0.80 | Memory is less burst-tolerant than CPU |
| OS overhead | 4–8 GB per node | kubelet, container runtime, system daemons |

**Example**: 500 pods × 512 MiB ÷ 0.80 = 320 GiB for pods + 8 GiB OS overhead per node × 45 nodes = 360 GiB → total ~680 GiB across the cluster.

### Storage IOPS

```bash
Required IOPS = (Read IOPS + Write IOPS) × Replication factor
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Read IOPS | Workload-dependent | Measure with `iostat` or application metrics |
| Write IOPS | Workload-dependent | Usually higher than read for logging/metrics |
| Replication factor | 3 (Ceph default) | 3 copies of every object |

**Example**: 10,000 read IOPS + 20,000 write IOPS × 3 = 90,000 IOPS across the Ceph cluster. With 200 IOPS per SSD, that is 450 SSDs minimum.

### Storage capacity

```bash
Required capacity = (Raw data × Replication factor) / (1 − Utilization headroom)
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Raw data | Current + growth | Include WAL, snapshots, logs |
| Replication factor | 3 (Ceph), 2 (RAID1) | Ceph default is 3x |
| Utilization headroom | 0.85 | Keep 15% free for rebalancing |

**Example**: 10 TiB raw data × 3 ÷ 0.85 = 35.3 TiB raw capacity → provision 40 TiB.

### Network bandwidth

```bash
Required bandwidth = (Expected traffic × Growth factor) / Utilization target
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Expected traffic | Peak Gbps | Measure at the load balancer |
| Growth factor | 1.5–2.0 | 12–24 months ahead |
| Utilization target | 0.60 | Leave headroom for spikes |

**Example**: 10 Gbps peak × 1.5 ÷ 0.60 = 25 Gbps → provision 25–40 Gbps fabric.

### etcd disk IOPS

```bash
etcd commit latency must stay under 25 ms p99. Required IOPS = (Writes per second × WAL size) / Disk block size
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Writes per second | Workload-dependent | Kubernetes API writes |
| WAL size | ~4–8 KB | etcd WAL entry size |
| Disk block size | 4 KB | Typical NVMe block |

**Example**: 500 writes/sec × 8 KB ÷ 4 KB = 1,000 IOPS minimum per etcd member. Use dedicated NVMe; monitor `etcd_disk_backend_commit_duration_seconds` — p99 above 25 ms means the disk is the bottleneck.

### Ceph OSD count

```bash
Required OSDs = Required IOPS ÷ IOPS per OSD
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Required IOPS | From storage IOPS formula above | Aggregate cluster IOPS |
| IOPS per OSD | 200–500 | NVMe: ~500; SATA SSD: ~200; HDD: ~100 |

**Example**: 90,000 IOPS ÷ 500 IOPS per NVMe OSD = 180 OSDs → 18 OSD nodes × 10 NVMe drives each.

### Kubernetes node count

```bash
Required worker nodes = Required vCPU ÷ vCPU per node
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Required vCPU | From CPU formula above | Aggregate cluster vCPU |
| vCPU per node | 8–32 | Choose your node size |

**Example**: 360 vCPU ÷ 16 vCPU per node = 23 nodes → round up to 24 for headroom.

### Load balancer count

```bash
Required LB nodes = Expected concurrent connections / Connections per LB node
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Expected concurrent connections | Peak at the LB | Measure at ingress |
| Connections per LB node | 10,000–50,000 | Depends on instance size and keepalive settings |

**Example**: 100,000 concurrent connections ÷ 25,000 per LB = 4 LB nodes → deploy 4 for HA (2 pairs).

### GitLab

```bash
Required vCPU = (Concurrent CI jobs × Cores per job) / Utilization target
Required RAM = (Concurrent CI jobs × RAM per job) / Utilization target + 8 GB overhead
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Concurrent CI jobs | Peak simultaneous pipelines | Measure in GitLab CI |
| Cores per job | 1–4 | Job-dependent |
| RAM per job | 1–4 GB | Job-dependent |
| Utilization target | 0.70 | Keep headroom |

**Example**: 20 concurrent CI jobs × 2 cores ÷ 0.70 = 58 vCPU → 60 vCPU. 20 × 4 GB ÷ 0.70 = 114 GB → 128 GB RAM.

### Monitoring (Prometheus)

```bash
Required disk = (Samples per second × Retention days × Bytes per sample) × 2
```bash

| Variable | Typical value | Notes |
| --- | --- | --- |
| Samples per second | Prometheus `prometheus_tsdb_head_samples_appended_total` rate | Measure on existing instance |
| Retention days | 15–30 | Configurable via `--storage.tsdb.retention.time` |
| Bytes per sample | ~2 | Prometheus TSDB average |
| Factor 2 | Compaction headroom | Prometheus needs headroom for compaction |

**Example**: 50,000 samples/sec × 86,400 sec/day × 15 days × 2 bytes × 2 = 259 TiB → provision 300 TiB.

## Worked example: 500-pod production cluster

| Step | Calculation | Result |
| --- | --- | --- |
| CPU | 500 pods × 0.5 cores ÷ 0.70 | 358 vCPU → 360 |
| Memory | 500 × 512 MiB ÷ 0.80 + 360 GiB OS | 680 GiB |
| Worker nodes | 360 vCPU ÷ 16 per node | 23 → 24 nodes |
| Storage IOPS | (10k read + 20k write) × 3 | 90,000 IOPS |
| Ceph OSDs | 90,000 ÷ 500 per NVMe OSD | 180 OSDs |
| etcd IOPS | 500 writes × 8 KB ÷ 4 KB | 1,000 IOPS |
| LB nodes | 100k connections ÷ 25k per LB | 4 nodes |
| Monitoring disk | 50k samples × 86,400 × 15 × 2 B × 2 | 259 TiB → 300 TiB |

## Validation

- Monitor `etcd_disk_backend_commit_duration_seconds` p99; alert above 25 ms
- Monitor node CPU/memory utilization; alert above 70% CPU or 80% memory
- Monitor Ceph OSD utilization; alert above 85% capacity
- Review sizing quarterly against actual metrics from Prometheus/Grafana
