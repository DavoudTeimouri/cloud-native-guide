    Rook-Ceph Production Architecture¶

    A. Failure Domains¶

    Node, Rack, and Zone Layout¶

    Failure domain Typical scope Recommended placement Impact if lost
    Node Single physical/virtual host Each MON/OSD runs on a distinct host Loss of one host → one MON, one or more OSDs lost; tolerated by quorum/replication
    Rack Physical rack of servers Spread MON nodes across racks; spread OSD hosts across racks Rack power/network failure loses all nodes in that rack
    Zone Availability zone / data center Across zones when multi-region Zone loss → full failover to another region
    CRUSH bucket root > zone > rack > host > osd Define in CRUSH map; align with infrastructure labels Misconfigured CRUSH buckets cause incorrect replica placement and increased data loss risk

    Recommended CRUSH hierarchy for production¶

    # Example CRUSH map structure (declared via CephCluster spec)
crushdeviceclass: hdd   # or ssd
crushlocation:
  rack: rack-id   # per-node label, e.g. node.label.rack
  host: node-hostname   # minion/k8s node name
    • 3-replica pools: CRUSH should spread replicas across distinct failure domains (rack/zone). Rook sets failureDomain: host by default; promote to rack or zone when the topology is known.
    • Erasure-coded pools: CRUSH placement is more restrictive; typically 1 replica per failure domain, then EC stripes across domains.

    Failure domain enforcement¶

    • Add node labels reflecting the physical topology (e.g., failure-domain.beta.kubernetes.io/rack, failure-domain.beta.kubernetes.io/zone).
    • Rook's CephCluster.spec.mon.count and spec.osd.DeviceFilter respect these labels when distributing OSDs and MONs.
    • Verify with ceph osd tree after deployment.

    B. MON Placement¶

    Count and quorum¶

    • Minimum: 3 MONs (odd number required for quorum). 2 MONs provide no quorum advantage over 1 and are discouraged.
    • Maximum: 5 MONs in most deployments; beyond that, management overhead outweighs benefit.
    • Quorum formula: floor(N/2) + 1 MONs must be online for the cluster to operate.

    Placement rules¶

    • Never co-locate a MON with an OSD on the same host if the host is the only OSD for a pool; doing so combines the monitor store and OSD database on one failure point.
    • Separate racks/azs: Each of the 3 MONs should run on a different rack/availability zone when possible.
    • Dedicated resources: MONs need modest CPU and RAM (typically 2 vCPU, 4 GiB), but require local SSD for the MON store and OSD database/WAL. Do not share the OSD data disk with the MON store.
    • Node selector: Use spec.mon.nodeSelector or node labels to guarantee MON pods land on dedicated storage hosts.

    Example CephCluster MON spec¶

    mon:
  count: 3
  allowMultiplePerNode: false
  # nodeSelector:
  #   failure-domain.beta.kubernetes.io/zone: zone-a

    C. OSD Topology¶

    Device allocation¶

    • One OSD daemon per data disk (do not over-provision OSDs per disk; the OSD daemon maps 1:1 to a block device).
    • Use raw device mapping (disk passthrough) for OSD data disks; never share a virtual disk with the host OS or other containers.
    • Device classes: declare spec.osd.deviceClass: ssd or hdd in the CephCluster spec; Rook tags OSDs accordingly, and CRUSH buckets can use the class for placement.

    OSD topology in CRUSH¶

    • Rook automatically generates a CRUSH map where each OSD is under its host node, and nodes are under the configured failure domains (rack/zone).
    • If failureDomain: host is set in pools, Rook places replicas across distinct hosts. For rack/zone awareness, set failureDomain: rack or failureDomain: zone in the pool spec and ensure node labels match.

    Recommended OSD-to-host ratio¶

    Disk type OSDs per host OSD journal type Notes
    NVMe SSD 1–2 (one per NVMe namespace or device) Battery-backed or flush‑nvme Highest IOPS; keep 1 OSD per namespace for best performance
    SATA SSD 2–4 (shared device if capacity allows) Battery-backed write-back Moderate IOPS; balance with journal size
    HDD 1 per physical disk Internal (no battery) One OSD per disk is mandatory; journals on separate SSD if possible

    OSD resource minimums¶

    # In CephCluster spec, under storage.osd.resources.requests
osd:
  requests:
    cpu: "2"
    memory: 4Gi
    • Adjust upward for OSDs that host many PGs (placement groups). A rule of thumb: ~1 vCPU per 50–100 PGs, and 1 GiB RAM per 20–50 PGs, depending on workload.

    D. CRUSH Hierarchy¶

    Default CRUSH map generated by Rook¶

    Rook generates a CRUSH map with the following structure (customizable via spec.crushRoot and node labels):

    root
  region
    rack
      host
        osd.0
        osd.1
        ...
    • crushRoot: can be overridden in CephCluster.spec (default: default). Set to a meaningful geographic/regional root when running multi-region or when the default conflicts with site policies.
    • Failure domain labels: ensure node labels map to the CRUSH hierarchy. Rook reads failure-domain.beta.kubernetes.io/rack and failure-domain.beta.kubernetes.io/zone from nodes and inserts them into the CRUSH map automatically.

    Customizing the CRUSH map¶

    1. Add site-specific bucket types via ceph osd crush add-bucket if the default hierarchy is insufficient.
    2. Map nodes to buckets using labels: Rook does this automatically when failureDomain is set in the CephCluster/CephBlockPool spec.
    3. Verify with: 
      ceph osd tree
# confirms the rack/zone/region hierarchy and OSD distribution

    E. Capacity Planning¶

    Usable capacity formulas¶

    Pool type Formula Typical usable %
    3-replica (3x) usable = total_raw × (1 / 3) ~33%
    Erasure coded (k+m) usable = total_raw × (k / (k + m)) 4+2 → ~57%; 6+3 → ~67%
    With reserved fraction usable_raw = Σ(disk_size) × (1 - reserved_fraction) reserved_fraction = 0.05–0.10

    Example: 3-replica pool with 4 TB disks, 5% reserved¶

    raw_total = 12 disks × 4 TB = 48 TB
reserved  = 48 TB × 0.05 = 2.4 TB
usable_raw = 48 TB - 2.4 TB = 45.6 TB
usable_3x   = 45.6 TB / 3 = 15.2 TB

    Storage headroom¶

    • Keep 25–30% of raw capacity free at all times. This headroom allows an OSD replacement + rebalancing without the pool filling to 100%.
    • Monitor osd_pool_used_bytes and osd_pool_percent_used; set alerts at 70%, 80%, and 90% of usable capacity.

    IOPS and network planning¶

    Metric Guideline
    3× write amplification Each client write lands on 2 OSDs (replica + client acknowledgement), so effective write throughput ≈ 1/2 of raw disk bandwidth.
    10 GbE network Supports ~1.25 GB/s sustained; a 3× pool writing at >1 GB/s client rate will saturate the link.
    Disk IOPS NVMe SSD: 100k–500k per device; SATA SSD: 30k–80k; HDD: 100–180 random 4k IOPS. Size from expected PG count and expected TPS.

    F. Production Sizing Guidelines¶

    Step 1: Define workload profile¶

    Profile Typical R/W ratio IOPS per TiB Notes
    Database (OLTP) 80/20 read/write 20k–200k random 4k IOPS/TiB Use 3-replica pools; EC is not recommended
    File server 70/30 read/write 5k–50k random 4k IOPS/TiB Can use EC for capacity efficiency
    Backup/archive 90/10 read/write 1k–5k sequential IOPS/TiB EC (6+3) is cost-effective

    Step 2: Calculate raw disk count¶

    disks_needed = (target_usable_tb × replica_factor) / disk_size_tb
replica_factor = 3 for 3x, or (k+m)/k for EC
add 10–20% spare for unexpected failures

    Step 3: Determine host count¶

    • MONs: 3 hosts minimum (ideally separate racks/azs).
    • OSD hosts: Minimum 3 hosts for a fault‑tolerant cluster (each host holds at least one OSD, and the failure of any one host does not lose data because replicas are on other hosts).
    • Desired hosts: ceil(disks_needed / osds_per_host) + 1 (the extra host is the spare/standby).

    Step 4: Resource per host¶

    Role vCPU RAM Disk
    MON 2 4 GiB 1× 200–500 GiB SSD (local, dedicated)
    OSD 2–8 (depends on PG count) 4–16 GiB 1× data disk (HDD/SSD/NVMe) + optional journal SSD
    MGR 1 2 GiB — (co-located with MON or OSD)
    MDS (if CephFS) 1 2 GiB — (co-located)
    RGW (if S3) 2 4 GiB — (can co-locate with OSD)

    Step 5: Validate against RPO/RTO¶

    • RPO (Recovery Point Objective): With 3-replica synchronous replication (default in Rook), RPO = 0 bytes (no data loss) as long as ≥ 2 replicas survive. With async replication across regions, RPO is determined by WAL archiving frequency.
    • RTO (Recovery Time Objective): Measured by running a restore drill (see the DBRE backup & recovery checklist). Typical RTO for Rook-Ceph with base backup + WAL replay: 15–30 minutes for a single-node loss, 45–90 minutes for a full-region failover.

    Step 6: Checklist before going production¶

    • [ ] 3 MONs on separate hosts/racks/azs, each with local SSD MON store
    • [ ] OSDs deployed on ≥ 3 hosts, one OSD per data disk, device classes declared
    • [ ] CRUSH hierarchy reflects physical topology (rack/zone labels on nodes)
    • [ ] Pools have failureDomain: rack (or zone) and replicated.size: 3
    • [ ] 25–30% raw capacity headroom reserved
    • [ ] IOPS and network bandwidth validated against peak workload
    • [ ] Resource requests set per OSD host (CPU/memory for expected PG count)
    • [ ] ceph osd tree verified and matches physical layout
    • [ ] Backup strategy (WAL archiving + periodic base backup) documented and restore drills scheduled
