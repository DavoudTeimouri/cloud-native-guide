    Certificate Lifecycle Management¶

    Purpose and scope¶

    Document certificate lifecycle management for Kubespray-deployed Kubernetes clusters. Cross-references kubespray/kubespray-deployment.md §Certificate renewal, kubespray/certificate-lifecycle.md, and kubernetes/control-plane/index.md §Certificate expiry.

    Certificate types managed by Kubespray¶

    Certificate Managed by Location Rotation method
    kube-apiserver Kubespray PKI /etc/kubernetes/pki/apiserver.crt cluster.yml
    kubelet Kubespray PKI /etc/kubernetes/pki/kubelet.crt cluster.yml
    front-proxy-client Kubespray PKI /etc/kubernetes/pki/front-proxy-client.crt cluster.yml
    etcd server/client Kubespray PKI /etc/kubernetes/pki/etcd/ cluster.yml
    service account Kubespray PKI /etc/kubernetes/pki/sa.key, sa.crt cluster.yml
    OIDC CA Manual (owner-operated) /etc/kubernetes/pki/oidc-ca.crt Manual replacement

    Kubespray certificate renewal¶

    Kubespray manages Kubernetes internal PKI. Certificates are renewed by running cluster.yml:

    # Renew all certificates managed by Kubespray
ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b

# Renew certificates on specific nodes only
ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b --limit <node>

    Kubespray regenerates certificates on each run if they are expired or approaching expiry. The renewal is automatic — no manual certificate generation is required.

    Rotation procedure¶

    1. Update cluster.yml if certificate parameters changed
    2. Run cluster.yml -b on all control-plane nodes
    3. Run cluster.yml -b on all worker nodes
    4. Verify: kubectl get nodes shows all Ready
    5. Verify: kubectl get --raw='/readyz?verbose' returns all ok

    etcd certificate rotation¶

    etcd certificates are managed by Kubespray as part of the control plane. Rotation follows the same cluster.yml procedure:

    # Rotate etcd certificates on one control-plane node at a time
ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b --limit k8s-cp-1

# Verify etcd health after rotation
kubectl -n kube-system exec etcd-k8s-cp-1 -- etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt \
  --key=/etc/kubernetes/pki/etcd/healthcheck-client.key \
  endpoint health --cluster

    One control-plane node at a time — never rotate etcd certificates on all control-plane nodes simultaneously.

    kubelet certificate renewal¶

    kubelet certificates are regenerated by Kubespray during cluster.yml execution. For manual renewal or rotation outside the standard workflow:

    1. Ensure the kubelet static pod is running on the target node
    2. Run cluster.yml -b --limit <node> to regenerate the kubelet client certificate and key
    3. Restart the kubelet: systemctl restart kubelet or kubelet --rotate-certificates
    4. Verify: kubectl get nodes shows the node Ready
    5. Repeat for each node, one at a time

    service account key rotation¶

    service account keys are managed by Kubespray and regenerated on cluster.yml run. To rotate service account keys:

    1. Update service-account-keys in cluster.yml if key parameters changed
    2. Run ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b
    3. Regenerate any secrets referencing the old service account key
    4. Verify: kubectl get secret <secret-name> -o jsonpath='{.data.ca\.key}' returns the new key
    5. Restart workloads that depend on the previous key if they fail to authenticate

    front-proxy certificate rotation¶

    front-proxy-client certificates are regenerated by Kubespray during cluster.yml execution. To rotate front-proxy certificates:

    1. Verify the front-proxy client configuration: front-proxy-client.crt and front-proxy-client.key in /etc/kubernetes/pki/
    2. Run ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b
    3. Verify: kubectl auth can-i --help works without errors
    4. Verify: API server logs show no front-proxy TLS errors

    CA rotation¶

    Internal CA (Kubespray-managed)¶

    The internal Kubernetes CA is managed by Kubespray. CA rotation is performed as part of the cluster.yml workflow:

    1. Update CA parameters in cluster.yml if the CA key or validity period changes
    2. Run ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b on all control-plane nodes
    3. Verify all certificates are regenerated with the new CA
    4. Rotate user-facing trust stores if the CA change affects external consumers

    CA rotation is destructive — existing certificates signed by the old CA will stop working. Plan CA rotation during a maintenance window with sufficient error budget.

    External CA (e.g., cert-manager, external PKI)¶

    The external CA is not managed by Kubespray. Follow the owner-operated procedure in kubespray/certificate-lifecycle.md §F for OIDC CA rotation principles, adapted for the specific external CA.

    Emergency renewal¶

    When to use emergency renewal¶

    • Certificate expiry within less than the standard rotation window
    • Compromised private key
    • Unexpected CA failure
    • Premature certificate revocation

    Emergency renewal procedure¶

    1. Assess impact: Determine which services and workloads will be affected
    2. Rotate affected certificates: Run ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b to regenerate all certificates managed by Kubespray
    3. Rotate compromised keys manually if Kubespray automation cannot reach affected nodes:
    4. Generate new key pair: openssl genrsa -out <name>.key 2048
    5. Generate new CSR: openssl req -new -key <name>.key -out <name>.csr
    6. Sign with appropriate CA: openssl x509 -req -in <name>.csr -CA <ca.crt> -CAkey <ca.key> -CAcreateserial -out <name>.crt -days 365
    7. Deploy new key/cert to the affected nodes
    8. Verify: Confirm all affected services are healthy (kubectl get nodes, kubectl get pods, API connectivity)
    9. Post-incident: Review root cause and update monitoring to provide earlier warning

    Emergency rollback¶

    If emergency renewal introduces issues:

    1. Restore previous certificates from backup
    2. Run ansible-playbook -i inventory/<cluster>/hosts.ini cluster.yml -b to re-establish the prior PKI state
    3. Verify service restoration
    4. Document the incident and update procedures to prevent recurrence

    Monitoring and detection¶

    Proactively monitor certificate expiration:

    # Check kube-apiserver certificate expiry
kubectl -n kube-system get secret <apiserver-cert-secret> -o yaml | \
  grep 'tls.crt:' | head -1 | awk '{print $2}' | base64 -d | \
  openssl x509 -noout -enddate

# Check all certificates on a node
find /etc/kubernetes/pki -name '*.crt' -exec sh -c 'echo "{}:"; openssl x509 -in "{}" -noout -enddate' \;

# Check etcd certificate expiry
kubectl -n kube-system exec etcd-<node> -- etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  certificate list

# Alert when certificates have less than 30 days remaining
# (configured in your monitoring system, e.g. Prometheus alerting)
